# RetargetApp BVH — исправленная тестовая копия (2026-10-25)

**Не заменяет AnimRetargetAndroid!** Это приложение другого разработчика; импорт персонажей FBX/BVH и экспорт **только BVH**. Оно не поддерживает GLB и не объединяет библиотеку анимаций в один GLB.

## Что исправлено после проверки

1. BVH: вращения теперь читаются как углы соответствующих осей X/Y/Z, независимо от порядка каналов ZXY, ZYX и других.
2. BVH: writer пишет значения **Z,Y,X** в объявленные каналы `Zrotation Yrotation Xrotation` (раньше писал X,Y,Z).
3. World-space bind delta: `srcGlobal * inverse(srcBind)` вместо обратного порядка, который неверен для некоммутирующих поворотов.
4. Определение единиц BVH смотрит на длины основных костей, а не только на позицию таза в первом кадре: помогает, если BVH in-place с нулевым корнем, а смещения в сантиметрах.
5. Добавлены JUnit-тесты для порядка вращений, world-space delta, масштабов и записи чисел с точками при русской локали.

**Проверено:** ядро Kotlin скомпилировано через kotlinc. На предоставленном `Walking_01_01.fbx` (41 кость) тест переноса исходной Mixamo-анимации на её же скелет: максимальная погрешность глобальных вращений около 0.07°. Экспорт→импорт BVH: до 0.054°. Эти числа относятся только к тесту с тем же скелетом и не подтверждают корректность движения на чужом риге. Готовый APK не собран и не протестирован на планшете.

**Ограничения исходника:** в приложении одна анимация за раз, ZIP берёт первый BVH, по умолчанию перенос ограничен 1500 кадрами, нет 3D-просмотра меша. Не все FBX-особенности (PreRotation, RotationOrder, разные единицы измерения) гарантированно обработаны. Нет GLB.

## Сборка

Android Studio: открыть эту папку `RetargetApp`, Build APK(s). Либо выложить содержимое папки `RetargetApp` в корень отдельной ветки GitHub — в `.github/workflows/build-apk.yml` есть автоматическая сборка debug APK.

# BVH Retargeter — перенос анимации на своего персонажа (Android APK)

Приложение берёт **скелет персонажа** (FBX или BVH) и **анимацию** (.bvh / ZIP от Mixamo / .fbx),
пересчитывает анимацию на скелет персонажа и сохраняет результат в **BVH**,
который открывается в Blender, Unity, Unreal, Godot.

## Версия 2 — что исправлено

Предыдущая версия могла «крутить и ломать» персонажа. Найдено и исправлено 5 реальных ошибок,
каждая проверена автотестами (end-to-end: парсер → ретаргет → запись → обратный разбор):

| # | Ошибка | Симптом | Исправление |
|---|--------|---------|-------------|
| 1 | Иерархия скелета искажалась в каждой точке ветвления (второй-третий ребёнок прицеплялся к последнему добавленному узлу) | Руки/ноги росли из головы, персонаж — монстр | `buildTarget`/`buildTargetFromBvh`: индекс родителя фиксируется до обхода детей |
| 2 | Дельта bind-позы применялась справа (`bind * delta`) | Направление сгиба локтя/колена зависело от roll кости — «выкрученные руки» | Дельта применяется слева, в мировых осях: `tgtGlobal = S * tgtBind` |
| 3 | Локальные вращения считались относительно **bind**-поворота родителя, а не анимированного | Вращение бёдер задваивалось вниз по цепочке — дикое вращение конечностей | Локал = inv(анимированный родитель) * кость |
| 4 | У корня BVH первыми каналами идут ПОЗИЦИИ, а код читал их как эйлеры (95 см → 95°!) | Мгновенный перекрут всего тела на ~90° | Отдельный индекс каналов вращения (`rotStart`) |
| 5 | Числа BVH писались через локаль телефона | На русском телефоне «0,95» вместо «0.95» — файл ломался | Форматирование через `Locale.US` |

## T-pose / A-pose — обрабатывается автоматически

Персонажи в **разных позах** (источник — T-pose, ваш персонаж — A-pose, и наоборот) — это нормальная
ситуация, алгоритм сам её учитывает: для каждой кости берётся её мировая ориентация в bind-позе
источника и цели, и переносится только *относительное* движение. Кадр, где источник в своей bind-позе,
даёт ровно bind-позу вашего персонажа — без сдвигов и скруток.

Приложение теперь **пишет в лог**, что оно определило:

```
• Источник: T-pose (руки ~90° от вертикали)
• Цель: A-pose (руки ~135° от вертикали)   ← разница учтена автоматически
• Системы координат совпадают (коррекция осей не нужна)
• Сопоставлено костей: 41 из 41; без пары: ...
```

Дополнительно: если цель экспортирована в Z-up (некоторые экспорты из Blender), а анимация в Y-up —
вертикальная ось корректируется автоматически.

## Как собрать APK

### Способ 1 — Android Studio (рекомендуется)
1. Установи Android Studio (https://developer.android.com/studio).
2. File → Open → выбери папку `RetargetApp`.
3. Дождись синхронизации Gradle (скачает Gradle 8.7 и SDK 34 автоматически).
4. Меню **Build → Build App Bundle(s) / APK(s) → Build APK(s)**.
5. APK появится в `app/build/outputs/apk/debug/app-debug.apk`.
   Кинь его на телефон и установи (разреши «установку из неизвестных источников»).

### Способ 2 — командная строка
```bash
# нужны JDK 17 и Android SDK (ANDROID_HOME прописан)
cd RetargetApp
gradle wrapper            # один раз, скачает gradlew
./gradlew assembleDebug
# результат: app/build/outputs/apk/debug/app-debug.apk
```

## Как пользоваться

1. **«Выбрать персонажа»** — твой риг: `.fbx` (например, экспорт персонажа) **или `.bvh`**
   (скелет, экспортированный из Blender: File → Export → BVH). Если в BVH есть анимация — она
   игнорируется, берётся только иерархия (bind-поза).
2. **«Выбрать анимацию»** — `.bvh` (Mixamo выдаёт BVH внутри ZIP — можно кинуть ZIP целиком) или `.fbx` с анимацией.
3. Опции:
   - *На месте* — убрать дрейф вперёд (корень стоит на месте);
   - *Посадить на землю* — автоматически ставит самую низкую точку стоп на уровень bind-позы.
4. **«Ретаргет → BVH»** — сохрани результат.
5. Импортируй BVH в свой редактор/движок и перенеси на персонажа: имена костей, иерархия и
   bind-поза совпадают с твоим скелетом, поэтому перенос теперь 1-в-1 (по именам костей).

## Как это работает

```
S(j,t)          = srcGlobal_j(t) * inv(srcBindGlobal_j)     — мировой «свинг» кости источника
tgtGlobal_j(t)  = S(j,t) * tgtBindGlobal_j                  — свинг прикладывается к bind-позе цели
tgtLocal_j(t)   = inv(tgtGlobal_parent(t)) * tgtGlobal_j(t) — локалы для BVH/движка
корень          = bind_цели + (позиция_источника(t) − bind_источника) * масштаб_ног
```

- bind-позы берутся у каждой стороны свои → разница T/A-поз, roll костей и PreRotation компенсируются;
- кости без пары (пальцы, твист-кости с нестандартными именами) едут вместе с анимированным родителем;
- пропорции скелета не искажаются: трансляции костей цели остаются родными.

## Ограничения

- FBX-парсер читает бинарный FBX 6.x–7.7 (скелет + кривые анимации). ASCII-FBX не читается.
- Список синонимов имён костей — в `Retargeter.kt` → `normalize()` (thigh→upleg, calf→leg,
  lowerarm→forearm, thumb01→handthumb1 и т.д., понимаются суффиксы `.L/_l/l_`). Если кость не
  нашла пару — она останется в bind-позе, приложение напишет об этом в лог.
- Персонаж в `.bvh` должен содержать секцию MOTION (обычный экспорт из Blender её всегда пишет).
